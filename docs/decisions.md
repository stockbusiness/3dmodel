# 判断記録（decisions）

正本：`docs/spec/3d_art_validation_spec_v1_1.md`（Ver.1.1 / 2026-09-08）
分類タグの定義は `CLAUDE.md` §2 に従う。

- `BLOCKER`：これが決まらないと次に進めない。ユーザーの入力が必要。
- `ASSUMPTION`：軽微な選択を自分で決めた。後から覆せる形で実装する。
- `DEFERRED`：フェーズB/C、または今回対象外として後送り。
- `SECURITY_REVIEW`：セキュリティ上ユーザーの確認が要る。
- `UNVERIFIED`：外部APIの仕様・モデルID・価格・SDK引数を公式資料で確認できていない。

## RESOLVED（ユーザー回答済み。2026-09-08）

### B-1 ブランチ運用の不一致 → 解決

回答：「ブランチは進めやすい方法で大丈夫」。

決定：全ステージをセッション指定の `claude/confirmation-needed-v9f1r7` で進め、ステージごとにコミットを分ける。`CLAUDE.md` §4 の「ステージごとにブランチを切る」は、ステージをまたいで先回りしないための規定と解釈し、その趣旨（1回の作業は1ステージ以下、ステージ完了時に VERSION と CHANGELOG を更新）は維持する。ブランチを分けない代わりに、ステージ境界はコミットと CHANGELOG で識別できるようにする。

### B-2 権限モデル → 解決（案1を採用、将来の分離に備える）

回答：「権限は管理者と講師は同じでいいが、将来的には権限を分ける可能性があります」。

決定：
- 全操作者を同等権限とし、枠追加・上限額変更・手動費用確定・reveal を「理由入力＋監査ログ必須」の操作として全員に開放する（仕様第2章に従う）。
- 将来の分離に備え、`operators.is_admin`（真偽値、既定 true）を A1 の時点で作る。フェーズAでは権限判定に使わず、値の記録のみ。
- 権限判定は `app/auth.py` の単一の関数（例 `require_admin_action()`）に集約し、フェーズAでは「ログイン済みなら許可」を返す実装にする。将来はこの関数の中身だけを `is_admin` 判定に差し替えれば分離できる。呼び出し側に権限判定を散らさない。

関連する SECURITY_REVIEW S-4（講師が上限額を変更できることの許容）は、上記の回答により許容として確定する。抑止は監査ログによる。

### B-3 講師アカウントと校正セット → 解決

回答：「講師アカウントは当面一つでいい」。

決定：
- A1 の初期アカウント作成 CLI は 1 アカウントから作成でき、追加も同じ CLI で行える形にする。
- 校正セット（仕様第10章・第6.6章）は A4 で機能として実装するが、校正対象件数の既定値を 5 件から **0 件**にする。仕様第10章が「最初の5件（設定で変更）」と定めているため、これは設定値の選択であり仕様変更ではない。
- 講師が 2 名になった時点で設定値を 5 に戻せば、2 名の独立評価と 2 段階差の警告がそのまま機能する。
- 1 名運用の間は、集計画面に「校正未実施」と表示し、評価基準のばらつきが検出されていないことを明示する。
