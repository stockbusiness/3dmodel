## RESOLVED（ユーザー回答済み。2026-09-08）

### B-1 ブランチ運用の不一致 → 解決

回答：「ブランチは進めやすい方法で大丈夫」。

決定：全ステージをセッション指定の `claude/confirmation-needed-v9f1r7` で進め、ステージごとにコミットを分ける。`CLAUDE.md` §4 の「ステージごとにブランチを切る」は、ステージをまたいで先回りしないための規定と解釈し、その趣旨（1回の作業は1ステージ以下、ステージ完了時に VERSION と CHANGELOG を更新）は維持する。ブランチを分けない代わりに、ステージ境界はコミットと CHANGELOG で識別できるようにする。

### B-2 権限モデル → 解決（案1を採用、将来の分離に備える）

回答：「権限は管理者と講師は同じでいいが、将来的には権限を分ける可能性があります」。

決定：
- 全操作者を同等権限とし、枠追加・上限額変更・手動費用確定・reveal を「理由入力＋監査ログ必須」の操作として全員に開放する（仕様第2章に従う）。
- 将来の分離に備え、`operators.is_admin`（真偽値、既定 true）を A1 の時点で作る。フェーズAでは権限判定に使わず、値の記録のみ。
- 権限判定は `app/auth.py` の単一の関数（例 `require_admin_action()`）に集約し、フェーズAでは「ログイン済みなら許可」を返す実装にする。将来はこの関数の中身だけを `is_admin` 判定に差し替えれば分離できる。呼び出し側に権限判定を散らさない。

関連する SECURITY_REVIEW S-4（講師が上限額を変更できることの許容）は、上記の回答により許容として確定する。抑止は監査ログによる。

### B-3 講師アカウントと校正セット → 解決

回答：「講師アカウントは当面一つでいい」。

決定：
- A1 の初期アカウント作成 CLI は 1 アカウントから作成でき、追加も同じ CLI で行える形にする。
- 校正セット（仕様第10章・第6.6章）は A4 で機能として実装するが、校正対象件数の既定値を 5 件から **0 件**にする。仕様第10章が「最初の5件（設定で変更）」と定めているため、これは設定値の選択であり仕様変更ではない。
- 講師が 2 名になった時点で設定値を 5 に戻せば、2 名の独立評価と 2 段階差の警告がそのまま機能する。
- 1 名運用の間は、集計画面に「校正未実施」と表示し、評価基準のばらつきが検出されていないことを明示する。

### T-15：教室の題材は「正面＋背面を並べた1枚」が多い（2026-09-09・利用者の申告）

「こんなケースが多いと思う」との申告である。

**これは現行のプリセットが想定していない入力である。**

| 項目 | 内容 |
| --- | --- |
| 現行 `tripo-standard` が呼ぶAPI | `image_to_model`（**1枚の画像＝1つの対象**） |

**A3.5 での扱い（この判断の実務上の結論）：**

- **試験画像は「対象1つにつき1枚」に統一する。** 正面＋背面が並んだ素材しか無い場合は、
  **正面だけを切り出して**使う。

  **「事業者の品質が低い」のか「入力の形が合っていなかった」のか区別できない**。
  A3.5 は品質の感触をつかむための5件であり、切り分けられない失敗に1件を使う余裕がない。
- この制約は `docs/early-check-plan.md` の画像選定条件に追記した。

**A3.5 の後に持ち越す検討（今は決めない）：**

多視点入力を扱うなら、`multiview_to_model` を使う別プリセット
（例：`tripo-multiview`）を足すことになる。ただしこれは
**仕様に無いプリセットの追加**であり、以下が揃うまで着手しない。

1. U-26（多視点の1件あたりの価格）が確認できること
2. 1つの題材に複数枚の画像を紐づけるデータの持ち方を仕様側で決めること

**この判断が変えないこと：** T-13（案A・Tripo のみ5件）の内容と見積 $1.50 は変わらない。

### T-16：教室のAIアートの実物5点を確認。**AIアートと画像→3Dの要求は正反対**（2026-09-09・BLOCKER に近い判断待ち）

利用者から、教室で実際に生成しているAIアートの例が5点示された
（猫の侍・桜と五重塔の風景・地球を抱く人物・サッカーのキーパー・時計に乗る人物の厚塗り作品）。
あわせて「これを3Dにしたらどうなる？　そもそも意味がある？」との問いがあった。

**この問いは仕様第16章 A3.5 の目的そのものである。**
仕様は A3.5 を「そもそも見込みがあるかの確認。見込みがないと判断すれば以降の実装を止められる」
と定めている。したがって**この問いに答えることが A3.5 であり、$1.50 で答えが出る。**

#### 判明した構造的な不一致

| AIアートが上手いこと | 画像→3D が要求すること |
| --- | --- |
| 映える構図（煽り・寄り・被写体を切る） | 対象の**全身**が入り、シルエットが閉じている |
| 背景込みの世界観 | **背景は無地**。対象と背景が分離できる |
| 被写界深度・光のにじみ・厚塗りの質感 | 全域にピント。輪郭が明確 |
| 絵として完成していること | **立体の手がかり**があること |

**絵として完成しているほど、画像→3D には向かない。** これは事業者の品質の問題ではなく、
入力に立体の情報が入っていないという問題である。

#### 仕様第10章の合格基準と突き合わせた結果

仕様第10章の評価軸は「元画像の特徴／**全周の形状**／色・模様／魅力・完成度／
スマホ表示操作性」で、**合格は5軸すべて4以上**である。

#### T-17 の記述の訂正：VRM の制約は当たらない

T-17 で「`rig_model` の仕様に VRM が無い」ことを制約として挙げたが、
**対象が自社のUnityアプリであれば VRM は不要である。**
VRM は cluster・VRChat のような**他社プラットフォームへ持ち込むための規格**であり、
自前のUnityアプリでは Unity の Humanoid リグを直接使う。
`rig_model(spec="mixamo", out_format="fbx")` は Unity の Humanoid に対応づけられる
標準的な経路である（**ただし品質と価格は未確認**。U-28・U-31）。

#### Unity と決まって確定すること

| 項目 | 内容 |
| --- | --- |
| **形式** | Unity が標準で読むのは **FBX**。**glTF/GLB は標準では読み込めず**、glTFast・UnityGLTF 等のパッケージが要る |
| **座標系** | Unity は**左手系 Y-up**、glTF は**右手系 Y-up**。取り込み時に反転の変換が入る（Unity の FBX 取り込みと glTFast はいずれもこの変換を行う） |
| **単位** | Unity は 1 unit = 1m が慣例。`convert_model` の `scale_factor` で合わせる |
| **マテリアル** | **URP / HDRP を使っている場合、取り込んだマテリアルはそのままでは表示されない**（シェーダーの差し替えが要る）。Built-in なら Standard シェーダーに載る |
| **頂点数** | Unity 自体に上限は無いが、**1メッシュが 65535 頂点を超えると 32bit インデックス**になる。モバイル配慮なら 65535 以下に収めるのが安全 |

| 販売経路 | **NFTマーケットにも繋げる。そこで売れる** |

#### これにより権利が「要件」から「成否そのもの」になった

T-17 で権利は「懸案から要件に昇格した」と書いたが、**販売を訴求するなら
権利は要件ではなく成否そのものである。持っていないものは売れない。**

| 事業者・プラン | 生成物の権利 | **売れるか** |
| --- | --- | --- |
| **Tripo 無料** | 規約第5.2.1条により**会社が保持** | **売れない。** 権利を持たないものをNFTにして売ることはできない |
| Tripo 有料 | 商用・非商用とも可（第1.6.3節。Outputs で競合モデル・サービスを作ることのみ禁止） | 売れる見込み |
| **Meshy Free** | **CC BY 4.0** | **売れるが、NFTの前提が壊れる**（下記） |
| Meshy Pro 以上 | Private license | 売れる見込み |

**CC BY 4.0 と NFT は噛み合わない。**
CC BY 4.0 は「表示を付ければ**誰でも自由に複製・再配布・商用利用してよい**」ライセンスである。
したがって**そのNFTを買っても独占性が得られない。** 同じモデルを誰でも無料で合法的に入手できる。
**NFTの希少性という前提が成立しない。**

**結論：販売を訴求するなら、無料プランは選択肢から消える。**
T-11（当面は両社とも無料。有料化は運用開始後）とは**両立しない。**

#### 記録の穴（実装上の具体的な問題）

`generations` テーブルは `provider`・`preset_snapshot_json`・`is_live`・
`provider_task_id` を記録しているが、**そのとき事業者のプランが無料だったか
有料だったかを記録していない**（`app/models/tables.py` で確認）。

**同じ `provider="tripo"` の成果物でも、無料プランで作ったものは売れず、
有料プランで作ったものは売れる。しかしシステムはその区別を持っていない。**

→ **後から「この作品は売れるのか」を判別できない。販売を前提にするなら致命的である。**

**修正提案（実装していない）：** `generations` に生成時の権利状態を記録する。
プラン種別、参照した規約の版、商用利用の可否。
**仕様第9章の `generations` の定義に無い項目**なので、勝手に足さない（CLAUDE.md 第1章）。

#### T-18 の記述の訂正：品質基準は緩められない。むしろ上がる

T-18 で「用途が置物なら背面の創作が許容され、仕様第10章の『全周の形状4以上』と
同じ厳しさは要らない可能性がある」と書いた。**販売を前提にするなら逆である。**

**買った人は全周を見る。展示するなら来場者が全周を見る。**
したがって「全周の形状」は緩めるどころか**必須の軸になる。**
**展示・販売を訴求するなら、品質基準は下げられない。**

これは T-16（AIアートが画像→3Dに向かない）の問題が**再び重くなる**ことを意味する。

#### B-10 の判断が意味すること

Tripo 規約第5.2.1条により無料利用者の Outputs の権利は Tripo が保持するためである。
**この5件の用途は「品質の見込みを目で見ること」だけになる。**

これは割り切りとして妥当である。品質が見込みなしなら有料プランに切り替える意味も無い。
**ただし次の取り違えが起きうるため、手順書に明記した**（`docs/early-check-plan.md` 第0.2節）。

| 起きうる取り違え | 対処 |
| --- | --- |
| 有料に切り替えた後、無料プランで作った成果物を実運用で使ってしまう | **権利は後から移らない。作り直しが必要。** 手順書に明記した |

**根本的な対処は T-19 の修正提案（`generations` に生成時の権利状態を持たせる）である。**
セット名による代替は暫定措置であり、実運用の前に本対応が要る。

| 4 | **同意文言が2と3を説明していること** | **T-10 が未着手**。学習利用の明記に加え、権利の帰属と販売の可能性を書く必要がある |

**「検討の余地あり」との回答なので、ここは確定させない。**
ただし**1が満たされない限り2〜4は意味を持たない**ため、
**実運用の開始と有料プランへの切替は同時でなければならない。**

#### 「まずは一連の流れを作りたい」への回答

### T-21：画像生成を本システムに取り込む案（2026-09-09・利用者の提案・**仕様の修正提案。未実装**）

利用者から提案があった。

> ユーザーが作りたいイメージを入力 → プロンプト変換 → 画像生成 → 確認 → 3D
> これなら入力した画像が3Dに向いていないなどの問題が回避できるのでは？

**技術的な筋は通っている。** T-16（AIアートが画像→3Dに向かない）は
「入力画像を選べない」ことが原因であり、**入力画像を自分で作れるなら原因が消える。**
`確認` を挟む設計も良い。**安い工程で高い工程を絞る**という順序になっている。

#### SDKに該当機能が揃っていた（**関数の存在のみ確認。価格は未確認**）

| 関数 | 引数 | 意味 |
| --- | --- | --- |
| `text_to_image` | `prompt`, **`negative_prompt`** | テキスト→画像。**`negative_prompt` で「背景・影・見切れ」を除外できる** |
| `generate_image` | `prompt`, `file`, `files`, `template`, **`t_pose`**, **`sketch_to_render`** | **`t_pose=True`** はリグ付けに必要な姿勢。**`sketch_to_render=True` は線画から絵を起こす** |
| `text_to_model` | `prompt`, `negative_prompt`, 3Dの各引数 | **テキストから直接3D。画像工程を飛ばす** |
| `generate_multiview_image` | `image` | **1枚から多視点画像を作る**（T-15 の裏返しの解決になる） |

`text_to_model` に `image_seed` があることから、内部で画像を作っている構造と推測されるが、
**推測であり確認していない。**

#### この案の最大の問題：技術は解決するが、権利は悪化する

**これが本記録の要点である。**

T-19・T-20 のとおり、利用者は**成果物を生徒の権利で売る**ことを目指している。
著作権の有無は「**人の創作的寄与**」の程度による個別判断である（文化庁 2024年）。

| 設計 | 人の創作的寄与 | 画像→3Dの技術的な相性 |
| --- | --- | --- |
| **生徒が絵を描く → 3D化**（現行） | **強い** | **弱い**（T-16 の問題） |
| **テキスト入力 → 全部AI**（提案そのまま） | **弱い。プロンプトのみでは足りないという見方が一般的** | **強い** |

**つまり技術的な相性と権利の強さが逆相関している。**
提案どおり「テキストだけ入れてAIが全部作る」にすると、
**T-16 は解決するが、B-11（生徒に権利）と NFT 販売の前提が弱くなる。**

#### 解決策の候補：`sketch_to_render`（**この案の最良の形**）

`generate_image(sketch_to_render=True, file=...)` は**線画・ラフから絵を起こす**機能である。

**生徒が描く（線画・ラフでよい）→ `sketch_to_render` で3D向けに整える → 確認 → 3D**

| この形の利点 | 内容 |
| --- | --- |
| **創作的寄与が残る** | 生徒が実際に描いている。権利の話が成立する余地が残る |
| **技術的な相性も得られる** | システム側が背景・構図・姿勢を3D向けに揃えられる |
| **教室の性格が変わらない** | 「絵を描く教室」のままである。テキスト入力だけの教室にはならない |

**推奨はこの形である。** ただし `sketch_to_render` の**品質・価格・実際の挙動は未確認**（U-34）。

#### プロンプト変換にLLMは要らない（最初は）

「プロンプト変換」に別のAI（LLM）を足すと、**3社目の事業者**が増える。
規約・キー・費用・未確認事項がもう一組増える。

**最初は定型で足りる。** `text_to_image` に `negative_prompt` があるため、
**3D向けの制約は固定文で表現できる。**

| 要素 | 実装方法 |
| --- | --- |
| 3D向けの条件（対象1つ・無地背景・全身・影なし） | **prompt の固定接尾辞** |
| 除外したいもの（背景・影・見切れ・複数対象・被写界深度） | **`negative_prompt` の固定文** |
| 題材ごとの差 | プリセットと同じ仕組みで持てる |

**定型なら決定的（同じ入力で同じ出力）で、試験も書ける。**
LLMを入れると出力が揺れ、試験が書けなくなる。**LLMは後から足せる。**

#### 仕様との関係（**修正提案。勝手に実装しない**）

| 箇所 | 現在 | 必要な変更 |
| --- | --- | --- |

| 第6.2章の出所分類 | 「教室の既存作品」「**3D向けに準備**」「実際の写真」「お手本」「運営・講師の自作」 | **「3D向けに準備」が既にある**ので、分類の追加は不要な可能性がある。ただし「本システムが生成した」ことは区別が要る |

**A3.5 が測るのは3D生成の工程であり、それは両方の設計に共通である。**

> 参加者登録、LINEログイン・通知、課金、予約、会員の利用権連携、代理店管理、
> 公開共有URL、**展示空間**、**アバター**、AR、Blender接続、GPUモデル自社運用、
> 自動品質採点、**AI画像生成**・自動背景除去。

さらに同章はこう定めている。

> **加工画像は外部で用意して追加アップロードできればよい。**
> 自動背景除去は品質変化と追加依存を生むため初版では組み込まない。

**つまり「画像は外部で作ってアップロードする」は仕様の決定事項である。**
利用者の見立て（ChatGPT で作ることになる）は**仕様の方針と一致している。**

**あわせて重要：仕様は「展示空間」と「アバター」もフェーズAの対象外としている。**
T-17〜T-19 で議論したメタバースでの展示・アバターは、**いずれも仕様上フェーズAの範囲外**である。

#### 「結局一緒か」への回答：**半分は一緒で、半分は違う**

| 一緒である点 | 違う点 |
| --- | --- |
| AI生成物であること | **制約を誰が握るか** |
| 著作権の薄さ（創作的寄与の問題） | **失敗の切り分けができるか** |
| 費用が利用者側で発生すること | **金を使う前に止められるか** |

**違いは「誰が生成するか」ではなく「3D向けの制約が守られるか」である。**

**ChatGPT・DALL-E 系は「見て良い絵」に最適化されており、3D向けには最適化されていない。**
放っておくと背景つき・映える構図・被写界深度つきの絵が出てくる。
**それは T-16 の問題そのものである。**
