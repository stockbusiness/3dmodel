版：1.1 ／ 作成日：2026-09-08 ／ 改訂日：2026-09-08 ／ 実装担当：Claude Code等の開発エージェント
対象：独立した運営・講師専用の品質検証版（フェーズA）

Ver.1.0からの変更点は末尾の「付録：Ver.1.0→1.1 改訂一覧」に修正前／修正後を記載する。

## 0. Claude Codeへの開始指示

この仕様書を読み、独立した新規プロジェクトとしてフェーズAを実装してください。計画の提示だけで終了せず、モックで起動できる画面・API・ワーカー・保存・テスト・起動手順まで完成させてください。既存AIアート教室のリポジトリと本番環境は変更しないでください。

最初に作業先のAGENTS.md等、既存ファイルとGit状態を確認し、ユーザーの変更を保持してください。実装判断は本仕様を基準とし、軽微な選択は記録して進めてください。外部APIの仕様・SDK引数・モデルID・価格は実装時に公式資料で確認し、確認日と採用バージョンを記録してください。存在しないSDK機能やモデル名を推測して実装しないでください。

APIキーがなくてもモックで全機能を完成させます。実課金の生成は、利用する認証情報と試験予算がユーザーから指定・承認されている範囲でのみ行います。キー不足はモック実装を止める理由にしません。キーをチャット、ソース、ログ、テスト結果に出さないでください。

完成報告では「実装済み」「モック検証済み」「実API検証済み」「未確認」を分けてください。モック結果を品質実績として扱わないでください。公開デプロイ（第3章の限定公開環境を除く）、既存教室接続、第三者への通知は今回の実装対象外です。

## 1. 目的と成功の定義

既存AIアート教室は、千ノ国を知ってもらい土地販売につなげる入口として運用している。画像生成体験の魅力を更新するため、3D生成体験の追加を検討する。

品質が悪い作品は信頼を損なうため、最初に運営・講師だけで実際の題材を比較する。今回の成果物は、3D生成の品質、成功率、再生成率、待ち時間、費用、講師作業時間を記録し、**授業に採用する題材タグと生成サービス**を第10章の判定表で決められる検証システムである。判断の単位は「サービス×題材タグ」であり、全題材を一括で合否判定しない。

「すべての画像を忠実に立体化できる」「高品質設定なら必ず改善する」は保証しない。背面等の見えない情報は補完される。Web表示用作品が対象で、印刷可能性、実寸精度、Unity利用の適合性は判定しない（ただし判定材料となる形状メトリクスは第9章のとおり記録する）。

## 2. フェーズと範囲

### フェーズA：今回必須

- 運営用ログイン。管理者と講師は同等権限の内部利用者とする。
- 検証セット作成、画像アップロード、原画像と加工画像の区別、画像ごとの利用同意の記録。
- TripoとMeshyの生成接続、モデル・設定の固定されたプリセット。
- 単社生成と、同じ入力画像を使った2社比較。比較評価はブラインド（評価確定までサービス名を伏せる）を既定とする。
- 永続化したタスク管理、画面を閉じた後の継続、再起動からの復旧。
- 元画像・モデル表示、品質評価、再生成、CSV出力。
- セット上限額と送信枠のハードキャップ、費用見積と手動確認済み実績の記録、講師の作業時間記録。
- 生成物の形状メトリクス（ポリゴン数・頂点数・テクスチャ枚数と解像度・バイト数）の自動記録。
- 外部通信不要のモックモードと小さなサンプルGLB。
- 実機・講師検証用の限定公開環境（第3章）。

### フェーズAで実装しないもの

参加者登録、LINEログイン・通知、課金、予約、会員の利用権連携、代理店管理、公開共有URL、展示空間、アバター、AR、Blender接続、GPUモデル自社運用、自動品質採点、AI画像生成・自動背景除去。

予算・課金基盤（費用の予約／確定／解除のライフサイクル、未確定額の相殺、参加者課金、為替の自動取得）はフェーズBで再設計する。フェーズAの費用管理は第11章の縮小版に限定し、Bの基盤を先取りして作らない。

加工画像は外部で用意して追加アップロードできればよい。自動背景除去は品質変化と追加依存を生むため初版では組み込まない。カメラ常時プレビューも不要。画像選択を基本とし、スマホのファイル選択で写真を扱う。

### 後続フェーズ

B：品質結果を基に参加者向けスマホ画面、利用枠、少人数体験。生徒作品の利用同意取得はBの体験会前に行う。
C：既存AIアート教室の会員・作品・LINEとのAPI接続。
AでB/Cの実装を前倒ししない。

## 3. 最小技術構成（本仕様の決定事項）

前案のReact＋PostgreSQL＋クラウド保存をフル導入する構成から、検証用途に縮小する。

| 要素 | 初版で採用する構成 |
| --- | --- |
| サーバー | Python 3.11、FastAPI、Uvicorn |
| 画面 | Jinja2テンプレート、通常のJavaScript、CSS。Reactは使わない |
| 3D表示 | Google model-viewer。バージョン固定した配布物をローカル配信 |
| DB | SQLite＋SQLAlchemy 2系＋Alembic。外部キー有効、WAL、busy timeout |
| ワーカー | 同じコードベースの別Pythonプロセス。DBから短い処理単位で取得 |
| ファイル | 公開ディレクトリ外のローカル永続ボリューム |
| 起動 | Docker Composeでwebとworker。共通dataボリューム |
| 限定公開 | 小型VPS1台に同じDocker Composeを配置。Caddyで自動HTTPS、前段にIP制限またはBasic認証、その内側に運営ログイン |
| 試験 | pytest、必要な画面動作のPlaywrightテスト |

単一ホストの少人数内部検証に限定する。SQLiteをネットワークファイルシステム上で使わず、複数ホストへ拡張しない。webは1 Uvicornプロセス、workerは1プロセスとする。外部タスク自体は複数進行でき、ワーカーが順番に状態を確認する。HTTP通信中にDBの書込トランザクションを保持しない。

ローカル開発では127.0.0.1へバインドする。講師の実機確認と後続のLINE内ブラウザ確認はHTTPSを前提とするため、限定公開環境は最初からVPS＋Caddy構成で用意し、LAN内公開やトンネルサービスを恒久手段にしない。VPSのFQDN・IP制限の許可元・Basic認証情報はユーザーが指定し、deploy/に設定例（ダミー値）を置く。

将来のPostgreSQL・オブジェクトストレージ移行に備え、DBアクセスと保存処理をサービス化するが、その移行実装は今回不要。外部API使用のためローカルGPUは不要。model-viewer表示には端末側で対応する描画環境が必要で、実機試験は別途行う。

## 5. 利用フロー

1. 運営がログインし、検証セットを作る。名称、目的、対象分類、上限額、想定人件費を入力。
2. 画像をアップロードし、題材分類・出所・利用同意（有無・取得日・範囲）を指定。画像が表示できることを確認。
3. 必要なら加工済み画像を追加。原画像は上書きしない。加工種別（選択式）とツール名を記録。
4. 今回送る画像を明示的に選ぶ。サムネイル、寸法、ハッシュ、同意状態を表示。
5. 単社生成／2社比較を選び、プリセット、概算費用、累積見積を確認。
6. 生成ボタンでローカル依頼を作成。ワーカーが外部送信しタスクIDを保存。
7. 受付・生成・保存の状態を表示。画面を閉じてもDBから復元。
8. 完成GLBを保存し、元画像と並べて表示。比較時はA/Bを切り替えて同じ画像に対する結果を見る。ブラインドモードではサービス名を伏せる。
9. 講師が全周・特徴・操作性を評価し、合格／再生成候補／題材不適を記録。評価確定後にA/Bのサービス名を開示する。
10. 再生成時は理由と変更箇所を入力。新しい履歴として生成し、前の結果を残す。
11. 集計画面で題材タグ・サービス・モデル・プリセット・初回/再生成を比較し、第10章の判定表を表示してCSVを出力。

失敗した作品を自動で合格扱いしない。モック・実APIの表示と集計を常時分離する。

## 6. 画面仕様

### 6.1 ログイン

内部利用者のみ。公開登録画面は作らない。初期アカウントはCLIで作成し、平文パスワードをGitやログに出さない。パスワードハッシュ、HttpOnly Cookieセッション、有効期限、ログアウト、CSRF対策を実装。初期パスワードの固定値は禁止。

### 6.2 検証セット・画像一覧

セット名、実/モック、件数、処理中、未評価、合格、見積累計／上限額を表示。分類は「教室の既存作品」「3D向けに準備」「実際の写真」「お手本」「運営・講師の自作」、題材タグは単体キャラ・動物・雑貨・人物・風景・複数対象・細部多め・その他。分類は登録後修正可能だが変更ログを残す。

画像ごとに利用同意の状態（同意あり／不要（自作・お手本等）／未取得）を表示する。「未取得」の画像は選択画面で明示し、実生成の対象に選べない。

### 6.3 画像詳細と生成受付

原画像・加工版を区別し、加工種別・ツール名・メモを表示。実行するサービスと固定プリセット、試行回数、費用見積を確認できる。キー未設定、価格未確認、無効プリセット、利用同意未取得、送信枠なし、上限額超過は実生成を選択不可とする。モデルIDなどの詳細は運営用の折りたたみ表示。

画像IDを選択して処理し、利用者入力の任意URLをサーバーに取得させない。ボタン連打防止はUIとサーバーの両方で実装。冪等キーはサーバーが画面描画時に発行してフォームに埋め込む（フォームトークン方式）。画面の再読込で新しいキーが発行され、同一フォームの再送は同じキーになる。

### 6.4 進捗・復旧

詳細画面は5秒程度、一覧は15〜30秒程度のポーリングで更新。進捗率はAPIが返すときのみ表示し、不明なら段階表示。架空の進捗率、必ず何秒で完成という表示はしない。受付からの経過時間と最終確認時刻を表示。

「通信確認待ち」「受付結果不明」「保存失敗」を生成失敗と区別する。安全な再確認・再ダウンロードを用意し、どの操作が追加課金の生成かを明記する。

### 6.5 品質比較

元画像＋モデル。PCは並列、スマホは縦並び。重いGLBを同時に複数読み込まず、スマホはモデル切替を基本にする。正面・横・背面への視点操作、自由回転、拡大、表示リセット、背景色切替を用意。正面は生成側の向きと必ずしも一致しないため講師が基準角度を調整できる。

**ブラインド評価モード（既定ON）**：比較の各結果を「A」「B」として表示し、A/Bへの割当は比較ごとにランダムに固定して保存する。評価が確定するまで、画面・HTML・APIレスポンス・ファイル名・URLにサービス名・モデルID・プリセット名を含めない。評価確定後、その比較についてのみ開示する。単社生成の画面では通常どおり表示してよい。運営はブラインドをOFFにできるが、OFFで行った評価は集計上「非ブラインド」として区別する。

形状だけを確認したい場合でも追加の有料生成を自動実行しない。ビューアー読込エラー・長時間待ちを表示し、ファイル再取得と外部生成を区別する。

生成物の形状メトリクス（第9章 artifacts）は評価に影響しないよう、評価確定後に折りたたみで表示する。

### 6.6 評価・集計

評価入力は第10章。CSVはUTF-8 BOM、表計算での数式実行を防ぐエスケープを行う。秘密鍵・署名URL・個人の写真URLをCSVに含めない。画像IDと生成IDから内部画面で追跡できる。

集計画面に第10章の判定表（サービス×題材タグ）を表示し、各セルに初回合格率・2回以内合格率・サンプル数・判定（採用候補／保留／不適／サンプル不足）を示す。

校正セット：セット内で「校正対象」に指定した生成結果（初期値：最初の5件）は、講師2名がそれぞれ評価するまで集計に含めない。2名の評価差が2段階以上の軸を画面で警告し、基準合わせの材料にする。

表示は日本語、本文16px以上を目安、十分な太さ・コントラスト、スマホのボタン44px以上を目安に設計。

## 7. API設計（ローカルAPIの提案契約）

全て認証必須。POST/PATCH等はCSRF検証。GETは状態を変更しない。

| メソッド・パス | 内容 |
| --- | --- |
| POST /api/experiments | 検証セット作成 |
| GET /api/experiments | 一覧 |
| GET /api/experiments/{id} | 詳細と集計、判定表 |
| POST /api/experiments/{id}/assets | multipartで原画像登録（同意情報を含む） |
| PATCH /api/assets/{id}/consent | 利用同意の登録・更新。監査ログ必須 |
| POST /api/assets/{id}/variants | 加工画像登録 |
| GET /api/assets/{id} | 原画像・加工版・試行履歴 |
| GET /api/presets | 利用可否、モデル、設定、価格の確認状態 |
| POST /api/generations | 単社生成受付、202応答 |
| POST /api/comparisons | 同一入力の2社比較をまとめて受付、202応答。A/B割当を返す（ブラインド中はサービス名を返さない） |
| GET /api/generations/{id} | 状態、費用、成果物、評価、メトリクス。ブラインド中はサービス名・モデルIDを省く |
| POST /api/generations/{id}/retry | 品質再生成。新ID、理由必須 |
| POST /api/generations/{id}/refresh | 状態の再確認をキューに登録。再生成しない |
| POST /api/generations/{id}/retry-download | 保存だけ再試行（download_failed、validation_failedから） |
| POST /api/generations/{id}/cancel | ローカル中止要望。外部中止成立と区別 |
| POST /api/generations/{id}/resolve-submission | 不明な外部受付の手動照合。証跡・メモ必須。結果は「紐付け」または「未作成確認」 |
| POST /api/generations/{id}/reviews | 評価登録・改訂。確定時にブラインド開示 |
| POST /api/comparisons/{id}/reveal | 運営による手動開示（評価未確定でも可、監査ログ必須） |
| GET /api/files/{id} | 認証付き画像/GLB配信 |
| GET /api/experiments/{id}/export.csv | 詳細・評価・費用・メトリクス・判定表の出力 |

受付ボディはasset_variant_id、preset_id、purpose（benchmark/classroom_simulation）、必要ならparent_generation_id。providerはpresetから確定し、任意の外部エンドポイントを受け取らない。

POST生成/比較/再生成にはIdempotency-Keyを必須とし、キーとリクエストハッシュを保存。同キー・同本文は既存結果、同キー・別本文は409。上限額判定と送信枠確認と依頼登録を同一短期トランザクションで行う。

比較依頼は同じ加工版のハッシュを固定し、2社分の上限見積を合算して上限額判定する。片方の失敗で他方を破棄しない。それぞれの生成IDと状態を返す。

## 8. 外部生成とワーカー

### 共通アダプター

- estimate(input, preset): 見積額・通貨・クレジット・価格版・上限額を返す。
- submit(input, preset): provider_task_id等を返す。SDKの作成系自動リトライを確認・制御する。
- fetch_status(provider_task_id): 正規化した状態、進捗、成果物情報、取得できた課金情報を返す。
- download_result(result): 許可された保存先から取得しローカル保存。
- cancel(provider_task_id): 実際に公式APIで対応している場合だけ実装。未対応はunsupported。

Tripo/Meshy/Mockを実装。APIレスポンス原文を画面へ直接返さず、秘密情報を除いた診断ログに限定する。プリセットに固定モデルID、SDK版、パラメーター、価格版を含め、過去実行を後から設定変更で書き換えない。

### 状態遷移

正常経路：queued → submitting → running → downloading → ready_for_review

分岐と復帰経路：

| 分岐状態 | 発生条件 | 復帰操作 | 復帰先 | 送信枠 |
| --- | --- | --- | --- | --- |
| submission_unknown | 送信タイムアウト、または送信成功とID保存の間で停止 | resolve-submission（紐付け） | running | 保持 |
| submission_unknown | 同上 | resolve-submission（未作成を運営が確認） | cancelled | 返却 |
| provider_failed | 事業者が失敗を返した | retry（品質再生成扱いではなく技術再送。理由必須） | 新IDでqueued | 返却（失敗した試行は枠を消費しない） |
| download_failed | 成果物取得の通信失敗 | retry-download | downloading | 保持 |
| validation_failed | 取得した成果物が検査NG | retry-download | downloading | 保持 |
| validation_failed | 再取得しても検査NGが続く | resolve-artifact（運営がprovider_failed相当と確定、証跡必須） | provider_failed | 返却 |
| monitoring_paused | 30分経過して完了しない | refresh | running | 保持 |
| cancelled | queuedで外部未送信を確認 | なし | — | 返却 |
| cancelled | 送信後に外部取消が成立 | なし | — | 保持（費用照合を続ける） |

品質判定（unreviewed/pass/retry_recommended/unsuitable）は上記の技術状態と別管理。

- API送信前にsubmittingと送信意図をコミットする。
- 応答でタスクIDを得たら直ちに保存する。
- 送信タイムアウト、または送信成功とID保存の間で停止した場合はsubmission_unknown。自動で再POSTしない。
- 事業者が保証する冪等キーが使える場合のみその契約に従う。保証がなければ事業者履歴で照合し、見つかったIDを手動ひも付けする。
- 「見つからない」だけで未課金・未作成を断定しない。解除や新規生成は運営の記録付き操作とする。
- provider_failedの費用は「失敗・要照合」として見積を残し、事業者側で課金されていないことを確認した後に運営が手動で0に確定する。
- runningの通信失敗は同じタスクIDを再確認。指数バックオフ＋ジッター、429のRetry-Afterを考慮。
- 初期ポーリング10秒、最大60秒。30分経過でmonitoring_pausedにし、外部失敗とは断定しない。手動再開可能。
- GLB保存失敗時は同じタスクの再ダウンロード。外部に新規生成しない。
- キャンセルはqueuedなら外部未送信を確認して取消。送信後は外部の取消可否を表示し、費用返却を保証しない。未取消タスクは状態・費用の照合を続ける。

### ワーカーの処理単位

ワーカーは1プロセスだが、以下により1件の長時間I/Oが他タスクの状態確認を止めないようにする。

- 「状態確認」と「ダウンロード」を別の処理単位とし、1ループで状態確認は全対象を順に行い、ダウンロードは1件のみ実行する。
- 全ての外部通信に接続・読取タイムアウトを付ける（送信30秒、状態確認30秒、ダウンロードは総時間上限を設定で持つ）。
- ダウンロードはストリーム保存し、1処理単位の中で他タスクの操作を行わない。
- DBロックを持ったまま外部通信しない。処理単位の開始時にclaim、終了時に結果をコミットする。

SQLiteではBEGIN IMMEDIATE等の短期トランザクションと条件付きUPDATEでclaimする。lease_owner/lease_untilを保存し、停止後の取得競合を防ぐ。lease_untilを過ぎた対象を別ワーカーIDが取得する際、submittingのままの対象はsubmission_unknownへ移して人の照合を待ち、再submitしない。SQLiteでSELECT FOR UPDATEが機能する前提にしない。DBロックを持ったままネットワーク待機しない。

初期同時外部タスク上限は全体2・各社1、設定で変更。実際のAPI上限以下に制限。APIにキーが設定されていてもLIVE_API_ENABLED=falseなら外部生成不可。モック時は外部通信を行わない。

形状メトリクスはGLB検査時にローカルで抽出し、外部サービスへ問い合わせない。抽出できない項目はnullとし、0と区別する。メトリクスは品質判定に使わず、記録のみとする。

原画像と原結果の上書き禁止。評価改訂は履歴追加、集計は最新評価を使用。合格なしの単価はゼロでなく「算出不可」。データ削除は初版では扱わず、バックアップから復元できる手順を用意する。

## 10. 品質評価と採用基準

### 5段階評価（人が入力）

1：使えない、2：大きな修正が必要、3：不満が残る、4：体験に使える、5：非常に良い。

評価軸：元画像の特徴、全周の形状、色・模様、魅力・完成度、スマホ表示操作性。
重大不具合タグ：顔の崩れ、部品欠損、余分な部品、融合、背面破綻、模様の大幅変更、背景混入、読込不可、操作不能、その他。

合格は5軸すべて4以上かつ重大不具合なしを初期ルールとする。スマホ未確認は未確認のままとし、教室利用合格を付けられない。検証中の暫定的な見栄え評価は保存できる。APIのsuccessと品質合格は別。

題材不適は技術的な永久不可の断定ではなく、今回の設定・費用・試行枠では教室対象にしないという判断。AI自動採点は今回実装しない。

### 評価の校正

セット内の最初の5件（設定で変更）を校正対象とし、講師2名が独立に評価する。2名の評価が2段階以上離れた軸があれば警告し、運営が基準を擦り合わせてから残りの評価に進む。校正対象の評価は2名分を保存し、集計には両者の平均ではなく後から運営が指定した1名分を使う（指定がなければ集計から除外）。

比較評価はブラインド（第6.5章）で行い、非ブラインドで行った評価は集計時に区別して表示する。

### 検証計画

初期30題材：運営・講師の自作作品20、3D向けに準備した画像10。生徒の既存作品は利用同意を取得したものに限り、初回30題材には原則含めない（同意取得はフェーズBの体験会前に行う）。題材タグは各タグ5件以上を目安に配分し、極端に偏らせない。

同じ入力版を2社で1回ずつ、最大60初回タスク。不合格のみ再生成し、最大120送信枠（provider_failedで返却された枠は含まない）。実際の開始は上限額の設定後。加工比較や追加設定検証を行う場合は、追加枠を事前設定して目的を分ける。

### 早期実感触（A3.5）

アダプター完成直後、画面完成を待たずに5題材×2社＝10件（$5程度）だけ実生成し、運営が目視する。目的は「そもそも見込みがあるか」の確認であり、この10件の評価は集計上「早期確認」として通常の検証とは分けて表示する。見込みがないと判断すれば以降の実装を止められる。

### 集計と判定表

各出所・題材タグ・サービス・モデル・プリセット別に表示。初回送信数、技術完了数、評価済み数、未評価数、初回合格数、2回以内合格題材数、脱落数を明示。

- 初回合格率＝初回合格数÷初回送信題材数。技術失敗を除外しない。未評価があれば暫定と表示。
- 品質のみ初回合格率＝初回合格数÷（初回送信題材数−技術失敗で評価に至らなかった題材数）。上と併記し、サービスの不安定さと品質の低さを分離して読めるようにする。
- 2回以内合格率＝初回または再生成で合格した題材数÷初回送信題材数。
- 保存成功率、講師作業時間、端末別読込時間も別集計。
- 受付〜readyまでの時間をp50/p95で表示し、成功した件数・停止件数を併記。

判定はサービス×題材タグの単位で行う。判定表の各セルは以下のルールで自動表示し、最終判断は運営が行う。閾値は設定値とし、初期値は仮置きである。

| 判定 | 条件（初期値） |
| --- | --- |
| サンプル不足 | そのセルの初回送信題材数が5未満 |
| 採用候補 | 2回以内合格率90%以上かつ初回合格率70%以上 |
| 保留 | 2回以内合格率70%以上90%未満 |
| 不適 | 2回以内合格率70%未満、または重大不具合タグの発生率50%以上 |

サービスの選定は「採用候補となった題材タグ数」が多い方を優先し、同数なら合格題材1件あたり費用が低い方、次にp95待ち時間が短い方とする。両社とも採用候補の題材タグが0であれば、今回の設定・費用では3D体験の授業導入を見送る判断材料とする。

授業投入時の目標として、採用した題材タグに絞った上で初回合格率90%以上、2回以内合格率95%以上、講師作業平均5分以内を仮目標とする。達成保証・実測値として表示しない。

30件で28件合格なら93.3%、29件なら96.7%。少数サンプルでの結果は一般化しない。判定表で採用候補となった題材タグを使用し、次の少人数体験会で再検証する。

## 11. 費用管理（フェーズA縮小版）

2026-09-08の参照値：Tripo画像→標準テクスチャ付き30credits、1credit=$0.01。HDテクスチャ+10、HD形状+20。設定適用可否とモデル系列は実装時に再確認。Meshyは画像生成のcredits表と購入単価を別に確認する。Tripoと同じcredit単価を仮定しない。料金参照URLは第4章。

フェーズAの実費は最大120送信枠でも数十ドル規模であるため、予約／確定／解除のライフサイクルは持たず、次の3点に限定する。

1. **上限額**：セット単位と全体（環境設定）の両方に上限額USDを入力必須。未設定時は実API生成を無効。
2. **受付判定**：「送信済み全件（失敗・要照合を含む）の上限見積の合計＋新規依頼の上限見積」が上限額を超えたら受付拒否。比較は2社分を合算して同一トランザクションで判定する。見積は常に上限側（HD等の追加料金を含む最大値）を採り、保守的に倒す。未確認の追加料金があり上限を見積もれないプリセットは実行不可。
3. **実績**：事業者の管理画面・請求履歴と週次または検証終了時に照合し、生成ごとにconfirmed_manualとして手動入力する。見積と実績は別の行として保存し、混ぜない。provider_failedはfailed_unreconciledとして残し、未課金を確認した後に0で確定する。

価格は管理設定の版付きデータ。事業者がconsumed_credits等を返しても、USD単価が未確認なら実費を断定せず参考表示に留める。返金も事業者確認後に反映する。

上限額の変更と手動費用入力は監査ログ必須。確定実費の合計が見積合計を超えた場合は警告を出し、新規生成を停止する。

画面は「見積累計」「手動確認済み実績」「失敗・要照合」「上限額との差」を表示。換算は利用者が指定した参考レートを使い、現在レートと偽らない。作業費＝入力した作業秒÷3600×設定時給。生成待ち時間と講師の実作業時間を混同しない。

集計は以下を分ける。
- ベンチマーク総費用：比較先・不合格・再生成を含む全試行。
- 候補サービスの運用試算：そのサービスだけの初回・再生成・作業費。
- 合格題材1件あたり費用：対象費用÷重複を除いた合格題材数。
- 保存・通信・LINE・開発費は生成API実費と別。未測定項目をゼロ扱いしない。

## 12. 入出力と保護

画像はPNG/JPEG/WebP、初期上限10MiB・20メガピクセル。拡張子だけでなくデコード検査。SVG・実行可能形式は不可。EXIF方向を正規化した送信用コピーを生成し、位置情報等を除去する。原画像は非公開保存。加工内容と送信用ファイルhashを記録。

利用同意がmissingの画像は外部送信を禁止し、サーバー側でも拒否する（UIの非活性だけに頼らない）。

結果はGLBを基本とする。ダウンロード上限100MiBを初期値、ストリーム保存・一時ファイル・検査後の原子的rename。形式ヘッダー、サイズ整合、参照資産、読込可否を確認し、HTML等をGLBとして受理しない。GLB内の任意外部URI参照を許可せず、参照先を自動取得しない。検査時に形状メトリクス（第9章）を抽出する。

利用者入力URLの取得は禁止。事業者結果のダウンロードはHTTPS・許可ホスト・DNS/IP検査・リダイレクトごとの再検査を行い、localhost/private/link-local等へ接続させない。SDKが独自にダウンロードする場合も同等の制限を満たすか確認する。

ファイルは認証API経由で配信。パストラバーサル禁止、内部保存キーはUUID、元ファイル名を保存パスに使わない。Range対応または必要な配信方式を実機で確認。CORSは必要な同一オリジン中心。CSPの外部接続は限定し、model-viewerをCDNのlatestから動的取得しない。ブラインド中の配信ファイル名・URLにサービス名を含めない。

APIキーはサーバー環境変数。ログにはBearerヘッダー、画像base64、署名URL、パスワードを出さない。HTTPレスポンスの生データも同様。ローカル開発のweb公開ポートは127.0.0.1へバインド。限定公開環境は第3章のVPS＋Caddy構成とし、Caddyの前段でIP制限またはBasic認証を必須にする。VPS上でもDBと保存物は公開ディレクトリ外に置き、Caddy経由以外の直接アクセスをファイアウォールで閉じる。

## 13. モックと障害試験

モックは、成功、事業者失敗、429、作成応答タイムアウト、長時間待機、ダウンロード失敗、不正GLB、上限額超過を切替可能にする。サンプルは自作の単純形状GLB等を用意し、合成データであると明示。実人物・有料素材を無断同梱しない。

必須の自動試験：
1. 同じ冪等キーを連打しても依頼が1件。
2. 2社比較の上限額が片方分しかなければ両方とも未送信。
3. 同時受付でも上限額と送信枠を超過しない。
4. 作成応答タイムアウト後に自動で再POSTしない。
5. タスクID保存済みで再起動すると、同じタスクを再確認する。
6. submitting中に停止した場合は不明状態へ移り、人による照合が必要。
7. 保存失敗は再取得だけを行い、課金生成を増やさない。
8. 2社の片方失敗でも他方の成果物と費用が残る。
9. 上限2回を画像加工・プリセット変更で回避できない。
10. 未認証の画像・GLB取得拒否、CSRF拒否、任意URL取得拒否。
11. 外部URI参照GLB・偽拡張子画像・過大ファイルを拒否。
12. モックと実API、未評価と合格、ブラインドと非ブラインド、早期確認と通常検証を集計で混同しない。
13. 手動費用入力の重複送信でも実績が二重計上されない。
14. ビューアーの読込失敗で操作不能・永久ローディングにならない。
15. 合格が0件・評価が0件・生成0件で除算エラーにならない。
16. lease期限切れの対象を新しいワーカーIDが取得したとき、submittingのままの対象はsubmission_unknownへ移り、再submitされない。
17. provider_failedで送信枠が返却され、submission_unknownでは返却されない。
18. ブラインド中の比較について、画面HTML・APIレスポンス・配信URL・ファイル名にサービス名・モデルID・プリセット名が含まれない。評価確定後は含まれる。
19. 利用同意がmissingの画像は、UIを迂回してAPIを直接叩いても外部送信されない。
20. ダウンロード中のタスクがあっても、他タスクの状態確認が同一ループ内で実行される。

テストは本番APIを自動呼び出さない。実API試験は明示的な有効化が必要。実機確認欄はiPhone Safari・Android Chrome、後続でLINE内。端末がない場合は未確認と記録し、ブラウザーエミュレーションだけで実機合格と報告しない。実機確認は第3章の限定公開環境で行う。

## 14. 将来接続のために残すもの

assetsにnullableのexternal_system、external_tenant_id、external_user_id、external_image_idを用意する。これらは参照情報であり認証根拠ではない。外部ID入力だけで本人になれるAPIは作らない。

保存層はsave/read/stat等の境界を持ち、ローカル実装のみ実装。生成サービスはUIから独立させる。将来接続方針をdocs/future-integration.mdに記載するだけで、LINE秘密鍵・会員情報は取得しない。

接続候補：既存教室で本人確認→短期・一度限りのコードをサーバー間検証→会員ひも付け→画像利用権確認→利用枠付与。作品完了のイベントIDを使って通知を重複排除。既存教室DBを新システムから直接書き換えない。接続時に改めて既存コード・DB・運用設定を確認する。

フェーズBで再設計する予算・課金基盤に備え、cost_entriesの種別列は拡張可能な文字列とし、generationsの枠消費フラグはBの利用枠管理へ引き継げる形にする。ただしBの実装はしない。
