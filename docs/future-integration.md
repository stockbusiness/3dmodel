# 将来接続の方針（仕様第14章）

フェーズCで既存AIアート教室（team478a/ai-art-school）と接続する可能性に備え、
本システム側で用意しているものと、意図的に用意していないものを記録する。

**フェーズAでは接続の実装を行わない。** LINEの秘密鍵や会員情報も取得しない。

## 用意しているもの

### 参照用の外部ID（`assets` テーブル）

`external_system`、`external_tenant_id`、`external_user_id`、`external_image_id`
をいずれも null 許容で持つ。

これらは**参照情報であり、認証の根拠ではない**。
外部IDを入力しただけで本人として扱われるAPIは作らない。
フェーズAではどこからも書き込まれず、値は常に null である。

### 保存層の境界

`app/services/storage.py` が `save_bytes` / `save_stream` / `save_file` /
`read_bytes` / `stat` / `exists` の境界を持つ。フェーズAはローカル実装のみ。
オブジェクトストレージへ移す場合はこのモジュールの差し替えで足りる。

### 生成サービスのUIからの独立

生成の受付・状態遷移は `app/services/generation.py` にあり、画面から独立している。
事業者ごとの差は `app/providers/` のアダプターに閉じ込める。

### フェーズBの予算・課金基盤への引き継ぎ

- `cost_entries.kind` は拡張可能な文字列（フェーズAは estimate / confirmed_manual /
  failed_unreconciled の3種別のみ）
- `generations.consumes_quota`（枠消費フラグ）はフェーズBの利用枠管理へ引き継げる形にしている

フェーズBの予算・課金基盤そのものは実装しない（仕様第2章）。

## 接続の候補手順（実装しない）

1. 既存教室側で本人確認する
2. 短期・一度限りのコードを発行し、サーバー間で検証する
3. 会員とひも付ける
4. 画像の利用権を確認する
5. 利用枠を付与する

作品完了のイベントIDを使って通知を重複排除する。
既存教室のDBを本システムから直接書き換えない。
接続時に、既存のコード・DB・運用設定を改めて確認する。

## 意図的に用意していないもの

- 外部IDだけで認証が通るエンドポイント
- 既存教室DBへの書き込み経路
- LINEの資格情報を保持する仕組み
- 公開共有URL（仕様第2章でフェーズA対象外）
